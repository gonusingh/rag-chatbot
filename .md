## The RAG Story (Never Forget This)
> Imagine you give someone 10 books and ask a question.
> A smart person doesn't re-read all 10 books.
> They scan the index, find relevant pages, read only those, then answer.
> **That's RAG. Exactly that.**

```
Your Documents     →    The 10 books
Text Extraction    →    Opening and reading the books
Chunking           →    Cutting books into individual pages
Embeddings         →    Giving each page a topic fingerprint
Vector Database    →    A smart index grouping similar fingerprints
User Query         →    Your question
Similarity Search  →    Finding pages whose fingerprint matches your question
Top-K Retrieval    →    Picking the 3-5 most relevant pages
LLM                →    The smart person who reads those pages and answers
```

---

## The Full RAG Flow (One Line)
```
Document → Extract → Chunk → Embed → Store → Query → Retrieve → LLM → Answer
```

# SESSION 1 — Text Extraction

## What is it?
Converting any file format (PDF, DOCX, XLSX, PPTX, TXT) or URL into a **plain Python string.**

Every file format stores data differently. None of them are plain text.
Your job: crack each format open and pull out clean readable text.

## Why do we need it?
Every step after extraction (chunking, embedding, search) **only understands plain text.**
A PDF is binary. An XLSX has rows and cells. A URL has HTML tags.
None of these can go directly into an LLM or embedding model.

## The Core Principle
> **Garbage In = Garbage Out**
> If extraction is messy — broken sentences, weird characters —
> every step after it suffers. Quality starts at extraction.

## How it works — Format by Format

| Format | Library | How it works |
|---|---|---|
| PDF | PyMuPDF (fitz) | open → iterate pages → `.get_text()` |
| DOCX | python-docx | `Document()` → iterate paragraphs → `.text` |
| XLSX | openpyxl | load_workbook → sheets → rows → cells |
| PPTX | python-pptx | Presentation → slides → shapes → text_frame |
| TXT | plain Python | `open()` → `.read()` |
| URL | requests + BeautifulSoup | fetch HTML → parse → `.get_text()` |

| What I use | Alternatives | Why I use mine |

| BeautifulSoup | scrapy, playwright | Simple pages, no JavaScript needed |
| requests | httpx, urllib | Simplest for basic scraping |

## Important Limitation — Images in Files
- Libraries only read the **text layer**
- Text inside images (scanned PDFs, screenshots in PPTX) = **NOT extracted**
- This is called needing **OCR** (Optical Character Recognition)
- Tools for OCR: `pytesseract` (open source), `AWS Textract` (cloud)
- **For this project:** we skip OCR (assignment doesn't require it)

## Interview Questions & Answers

**Q: Why can't you directly feed a PDF to an LLM?**
> PDFs are binary files. LLMs only understand plain text.
> You need to extract the text layer first.

**Q: What library did you use for PDF and why?**
> PyMuPDF (fitz) — fast, handles multi-page PDFs, gives clean text per page.

**Q: What's the challenge with URL extraction?**
> Some websites use JavaScript to load content dynamically.
> BeautifulSoup only reads static HTML.
> For JS-heavy sites you'd need Playwright or Selenium.

**Q: What is garbage in, garbage out in RAG context?**
> If extraction is messy — broken sentences, wrong characters —
> your chunks will be bad, embeddings inaccurate, LLM answers wrong.
> Quality of the entire RAG depends on extraction quality.

**Q: What about scanned PDFs?**
> Basic extraction gives empty string on scanned PDFs —
> there's no text layer, only image pixels.
> Production solution: add OCR using pytesseract or AWS Textract.
> Known limitation of this project, mentioned as a next step.

# SESSION 2 — Chunking

## What is it?
Splitting one large text string into smaller, manageable pieces called **chunks.**

After extraction you have one giant string (maybe 50,000 words).
Chunking breaks it into pieces of ~200-500 words each.

## Why do we need it?

**Reason 1 — Token Limits**
> LLMs have a maximum input size (called context window).
> GPT-4 = ~128,000 tokens. Sounds big, but a 100-page PDF can exceed this.
> You cannot send the entire document to GPT.

**Reason 2 — Cost**
> OpenAI charges per token. Sending 50,000 words every query = expensive.
> You only want to send the 3-5 most relevant chunks, not everything.

**Reason 3 — Accuracy**
> If you send everything, the LLM gets confused by irrelevant information.
> Sending only relevant chunks = sharper, more accurate answers.

## Types of Chunking

**1. Fixed Size Chunking** (what we use)
```
Split every N words or N characters regardless of sentence boundaries
Simple, fast, works well enough for most cases
```

**2. Sentence-Based Chunking**
```
Split at sentence endings (. ! ?)
More natural, but sentences can be very different lengths
Library: nltk or spacy
```

**3. Overlapping Chunking** (what we use — inside fixed size)
```
Each chunk shares some words with the next chunk
WHY: A sentence might start in chunk 3 and end in chunk 4
     Without overlap, that answer gets cut in half
     With overlap, the full sentence exists in at least one chunk
```

**4. Semantic Chunking** (advanced)
```
Split based on topic changes, not just size
Uses embeddings to detect when the topic shifts
Library: langchain SemanticChunker
```

## Visual Example of Overlap
```
Text:    [word1 word2 word3 word4 word5 word6 word7 word8 word9 word10]

chunk_size=5, overlap=2:

Chunk 1: [word1 word2 word3 word4 word5]
Chunk 2:             [word4 word5 word6 word7 word8]  ← word4,5 repeat
Chunk 3:                         [word7 word8 word9 word10]  ← word7,8 repeat

Without overlap:
Chunk 1: [word1 word2 word3 word4 word5]
Chunk 2: [word6 word7 word8 word9 word10]  ← clean cut, context lost
```

## What are the Alternatives?

| What I use | Alternatives | Difference |
|---|---|---|
| Fixed + Overlap (manual) | LangChain RecursiveCharacterTextSplitter | More intelligent splitting |
| Word-based splitting | Character-based splitting | Words = more natural |
| Fixed chunk size | Dynamic size by paragraph | Paragraphs = natural boundaries |

## Interview Questions & Answers

**Q: Why do we chunk documents?**
> Three reasons: LLM token limits, API cost reduction, and accuracy.
> We only want to retrieve and send the relevant parts, not the whole document.

**Q: What is chunk overlap and why is it important?**
> Overlap means consecutive chunks share some words.
> This ensures a sentence or idea that spans a chunk boundary
> is fully captured in at least one chunk.
> Without overlap, context gets cut in half at boundaries.

**Q: What chunk size did you use and why?**
> 500 words with 50-word overlap.
> 500 is large enough to contain complete ideas,
> small enough to stay focused and within token limits.

**Q: What's the problem with very small chunks?**
> They lose context. A 50-word chunk might be one sentence
> without enough surrounding information to be meaningful.

**Q: What's the problem with very large chunks?**
> They reduce retrieval precision. A 2000-word chunk might have
> the answer buried inside lots of irrelevant text.

# SESSION 3 — Embeddings

## What is it?
Converting text into a list of numbers (a **vector**) that captures its meaning.

```
"The cat sat on the mat"  →  [0.23, -0.87, 0.45, 0.12, ...]  (1536 numbers)
"A kitten rested on rug"  →  [0.21, -0.85, 0.43, 0.14, ...]  (very similar!)
"Stock market crashed"    →  [-0.67, 0.34, -0.12, 0.89, ...]  (very different)
```

Similar meaning = similar numbers = close in vector space.

## Why do we need it?
Computers cannot compare meaning of text directly.
But they CAN compare numbers.
Embeddings convert meaning → numbers so we can do math on meaning.

## How similarity works — Cosine Similarity
```
Two vectors are similar if they point in the same direction.
Cosine similarity = measure of angle between two vectors.

Score of 1.0  = identical meaning
Score of 0.9  = very similar
Score of 0.5  = somewhat related
Score of 0.0  = completely unrelated
Score of -1.0 = opposite meaning
```

## Interview Questions & Answers

**Q: What is an embedding?**
> A numerical representation of text that captures its semantic meaning.
> Similar texts have similar embeddings (close vectors in space).

**Q: Why 1536 dimensions?**
> OpenAI's ada-002 model produces 1536-dimensional vectors.
> More dimensions = more nuance captured = better similarity matching.

**Q: How does the model know what's similar?**
> It was trained on billions of text pairs labeled as similar or different.
> It learned which words and concepts appear in similar contexts.

**Q: Can you use a free embedding model?**
> Yes — HuggingFace sentence-transformers runs locally for free.
> `all-MiniLM-L6-v2` is popular — 384 dimensions, fast, good quality.
> Trade-off: slightly less accurate than OpenAI's model.

# SESSION 4 — Vector Database (FAISS)

## What is it?
A special database that stores vectors (embeddings) and can find the most similar ones extremely fast.

Regular databases search by exact match (find name = "John").
Vector databases search by similarity (find meaning closest to this query).

## Why do we need it?
After embedding all chunks, we have hundreds or thousands of vectors.
When a user asks a question, we embed the question and need to find
the most similar chunk vectors. FAISS does this in milliseconds.

## How FAISS Works Internally
```
1. You give FAISS all your vectors (chunks turned into numbers)
2. FAISS builds an index (like a smart address book for vectors)
3. When you search, FAISS finds vectors closest to your query vector
4. "Closest" = smallest angle between vectors (cosine) or
               smallest distance (euclidean)
5. Returns top K closest matches in milliseconds
```

## What is Top-K Retrieval?
```
top_k = 3 means: retrieve the 3 most relevant chunks

Why not top_k = 1?  → Might miss important context
Why not top_k = 20? → Too much text, LLM gets confused, costs more
Sweet spot: 3 to 5 chunks
```

## Interview Questions & Answers

**Q: What is a vector database?**
> A database optimized to store and search high-dimensional vectors.
> Unlike SQL which does exact matches, vector DBs find semantically similar items.

**Q: Why FAISS over Pinecone?**
> FAISS runs locally, free, no account needed — perfect for this project.
> Pinecone is cloud-based, scales to millions of vectors, better for production.

**Q: What is Top-K retrieval?**
> Retrieving the K most similar chunks to the user's query.
> We use K=3 to balance relevance and context without overwhelming the LLM.

**Q: Is FAISS persistent?**
> By default no — it lives in memory and resets when the program stops.
> You can save/load FAISS index with `faiss.write_index()` / `faiss.read_index()`.

# SESSION 5 — Retrieval + LLM + Source Display

## What is it?
The final step: take the retrieved chunks, pass them to GPT as context,
and ask it to answer the user's question using that context.

## Why not just ask GPT directly without RAG?
```
Without RAG:
→ GPT only knows what it was trained on (cutoff date)
→ GPT doesn't know YOUR documents
→ GPT might hallucinate (make up answers confidently)

With RAG:
→ GPT gets actual text from your documents as context
→ Answers are grounded in real content
→ You can show sources (which document the answer came from)
→ Works on ANY document, even uploaded today
```

## Where in code does this happen?
```python
# rag_pipeline.py
# ============================================================
# CONCEPT 5 — LLM INTEGRATION
# WHAT  : Sends retrieved chunks + user question to GPT
# WHY   : GPT generates a natural language answer using context
# WHERE : Called LAST, after retrieval
# HOW   : Chunks become the "context" in the prompt
# ============================================================

def generate_answer(query: str, relevant_chunks: list) -> str:
    # query           = user's question
    # relevant_chunks = top-K chunks from FAISS search
    # returns         = GPT's answer string

    prompt = f"""
    Use the following context to answer the question.
    If the answer is not in the context, say "I don't know."

    Context:
    {relevant_chunks}

    Question: {query}
    Answer:
    """
```

## The Prompt Is Everything
```
A good RAG prompt has 3 parts:

1. INSTRUCTION  → Tell GPT what to do with the context
2. CONTEXT      → The retrieved chunks (actual document text)
3. QUESTION     → The user's query

If GPT says "I don't know" → retrieval failed (wrong chunks returned)
If GPT makes things up    → context missing, GPT filling gaps
```

## Source Display
```
Along with the answer, show the user WHERE the answer came from.
This means storing metadata with each chunk:
  - which file it came from
  - which page/slide/row
  - the URL if it was a web source

Users can click the source and verify the answer themselves.
This builds TRUST in the chatbot.
```

## What are the Alternatives?

| What I use | Alternatives | Difference |
|---|---|---|
| OpenAI GPT-4 | GPT-3.5-turbo | Cheaper, slightly weaker |
| OpenAI GPT-4 | Llama 3 (Meta) | Free, open source, runs locally |
| OpenAI GPT-4 | Mistral | Open source, fast, good quality |
| OpenAI GPT-4 | Gemini (Google) | Strong alternative, multimodal |

## Interview Questions & Answers

**Q: What is hallucination in LLMs?**
> When an LLM generates confident-sounding but factually wrong answers.
> RAG reduces hallucination by giving the model real source text to work from.

**Q: What is a prompt in LLM context?**
> The full text input you send to the LLM.
> In RAG, the prompt = instruction + retrieved context + user question.

**Q: Why do you show sources alongside answers?**
> Transparency and trust. Users can verify the answer.
> It proves the chatbot answered from the document, not from hallucination.

**Q: What if the answer is not in any document?**
> The prompt explicitly instructs GPT: "If not in context, say I don't know."
> This prevents hallucination on out-of-scope questions.

# Key Terms Glossary

| Term | Simple Definition |
|---|---|
| RAG | Using your own documents to give LLM real context before answering |
| Token | ~1 word. LLMs charge per token and have max token limits |
| Embedding | Text converted to a list of numbers representing its meaning |
| Vector | A list of numbers. An embedding is a vector |
| Vector Database | Database that stores vectors and finds similar ones fast |
| FAISS | Facebook's library for fast similarity search |
| Chunk | A small piece of text cut from a large document |
| Overlap | Words shared between consecutive chunks to maintain context |
| Top-K | Retrieving K most similar chunks to the query |
| Cosine Similarity | Mathematical measure of how similar two vectors are (0 to 1) |
| Hallucination | LLM confidently generating wrong/made-up information |
| Context Window | Maximum tokens an LLM can receive in one request |
| Prompt | The full text input sent to an LLM |
| OCR | Optical Character Recognition — reading text from images |
| .env | File storing secret keys, never committed to GitHub |
